# Packaging and distribution: the evaluation

*Roadmap question: is the current microservice architecture suitable for
distributing Smoking Pi through apt, Homebrew and other package managers,
and what would have to change to offer a simple install and upgrade?*

**Answer: yes, as a package that manages a Compose deployment — not as
native packages of the services.** The stack is nine locally built container
images around four pinned upstream ones (SmokePing, InfluxDB, Grafana,
PostgreSQL); turning those into Debian packages would mean re-packaging four
upstream projects and their init logic, and would still need Docker for
nothing to be gained. What a package *can* do well is own the parts that are
currently the user's problem: where the code lives, where state lives, how
the stack starts at boot, how it upgrades, and how it goes away. An
end-to-end trial (below) built a working `.deb` from the current tree in
seconds; what it could not do is upgrade in place, because the tree is still
a runtime dependency. The backlog at the end is the list of changes that
close that gap, in order, with costs.

## What the system is, shaped for packaging

From the inventory (all counts as of v2.9.0):

- **Pro: 10 declared services, 5 always on** (smokeping, postgres,
  config-manager, web-admin, grafana), 1 near-mandatory profile
  (`influxdb`), 4 opt-in (`mcp`, `alerts`, `ai`, `clickhouse`). Standard: 4.
  Basic: 1.
- **9 images built on the target** from `shared/modules/*/Dockerfile`, 4
  of them thin wrappers over pinned upstream images, 5 `python:3.14-slim`
  apps. Building needs the internet four ways (apk, PyPI, a GitHub clone in
  config-manager, a Grafana plugin download). CI builds 4 of the 9, on
  amd64 only, and publishes none. **No registry, no version in any
  artifact**; the running code's identity is verified by the doctor hashing
  `.py` files against the checkout.
- **State**: 8 named volumes (10 with ClickHouse), two of which — PostgreSQL
  (the config source of truth) and InfluxDB (all history) — are pinned to
  their majors by hand because a major bump over a live volume initialises
  an empty cluster. Plus **git-tracked directories the running stack
  mutates** (`editions/pro/config-manager/{config,output}`) and a flat
  `.env` generated by `setup.sh` into the edition directory.
- **The checkout is a runtime dependency**, not just a build input: Compose
  bind-mounts source directories into containers (`smokeping-exporters`,
  `web-admin/app`, Grafana provisioning, SQL init), every `build:` and mount
  is `../../shared/...` relative to the edition directory, and
  config-manager needs the host's Docker socket to signal SmokePing.
- **Three services run on the host network** for reasons that do not go
  away: smokeping (raw ICMP, the real first hop, host IPv6, nl80211 for
  Wi-Fi), alerter and mcp-server (an OpenClaw gateway that listens only on
  the host's loopback).
- **Nothing starts the stack at boot** except Docker's restart policy;
  there is no unit, no uninstall, no upgrade command. Several helper
  scripts still hard-code container names from two layouts ago.

## The alternatives

| | A · native packages per service | B · split packages + metapackage | **C · one package that manages the Compose deployment** | D · installer script only |
| --- | --- | --- | --- | --- |
| What ships | SmokePing, Grafana, InfluxDB, PostgreSQL and the five Python apps as host services | Same, one package each, plus `smoking-pi` pulling them in | The stack definition, the `smoking-pi` command, a systemd unit; images pulled (or built) on first start | A `curl \| bash` that clones and runs `setup.sh` |
| Fits the architecture | No: four upstream projects would be re-packaged and their container init logic (s6, `custom-cont-init.d`, generated-config symlinks) rewritten for the host | No, and ×N | Yes: it packages what exists | Yes, but it packages nothing |
| Maintenance | Tracking four upstreams' packaging across distros; Grafana and InfluxDB already publish their own apt repos with their own opinions | Worse | The compose files and Dockerfiles, which are maintained anyway | Low, and nothing to show for it in `apt list` |
| Install / upgrade UX | `apt install`, but then a service-by-service configuration story | Same | `apt install smoking-pi && smoking-pi install`; `apt upgrade` + `smoking-pi upgrade` | Clone, run a script, re-run it later and hope |
| Boot, status, uninstall | systemd per service | Same | One unit, one command, `apt remove` keeps data | None |
| Effort | Months | Months | Days–weeks, see backlog | A day |
| Verdict | **No** | **No** | **Yes** | Stepping stone at most — the CLI from C works from a clone today, which covers this |

The one alternative that deserves a sentence is "simplify the local
deployment while keeping the internal modules" — that is what C requires as
its first step anyway (relocatable state, no source bind-mounts), so it is
not a competitor but the prerequisite.

## The trial

`packaging/deb/build.sh` builds `dist/smoking-pi_<version>_all.deb` from
the **committed tree at HEAD** (`git archive`, never the working tree — the
first build accidentally took the checkout, and the package carried the
reference Pi's generated target list). Contents: the tracked `editions/`,
`shared/`, `docs/`, `examples/` under `/opt/smoking-pi`; `packaging/smoking-pi`
as `/usr/bin/smoking-pi`; `packaging/systemd/smoking-pi.service`;
`/etc/default/smoking-pi` as a conffile; `postinst`/`prerm` that reload
systemd and disable the unit. `Depends: docker.io | docker-ce,
docker-compose-plugin | docker-compose-v2, openssl, python3, python3-yaml,
git`;
`Architecture: all` because the package holds no binaries — the images are
built or pulled per architecture at first start.

What worked, on the Pi, with no Docker involved in the build:

- Builds in about two seconds; 1.4 MB; some 370 files. `dpkg-deb --info` and
  `--contents` are what you would expect.
- Extracted into a scratch root (not installed on the reference Pi), the
  CLI runs from the `/opt`-style path: `smoking-pi version` reads 2.9.0
  from `CITATION.cff`; `smoking-pi paths` reports the edition, env file and
  profiles.
- **`docker compose config` succeeds from `/opt/smoking-pi/editions/pro`**
  with the `influxdb,mcp,alerts` profiles: the relative `../../shared`
  build contexts and mounts resolve under a fixed install prefix. The
  layout does not have to change for a package to work.
- The unit verifies (`systemd-analyze verify`, once `/usr/bin/smoking-pi`
  exists). Its start timeout is `infinity` on purpose: until images are
  pulled rather than built (#3), a cold first `up` can outlast any timeout,
  and systemd killing a build half-way is the worst outcome — so `install`
  is run interactively first and the unit handles every boot after.
- `smoking-pi install` refuses to run over an existing `.env`: `setup.sh`
  regenerates every secret, and the PostgreSQL and InfluxDB volumes keep
  the old ones. Re-running it is how a working stack stops authenticating
  to its own database — a hazard the inventory names and the CLI now
  guards against.

What the trial shows cannot work yet — each is a backlog item below:

1. **`.env` and the mutated config directories sit inside `/opt`.** A
   package upgrade replaces `/opt/smoking-pi`; `editions/pro/.env` would be
   orphaned or clobbered, and `config-manager/config/targets.yaml` — which
   the running stack rewrites and which was *tracked in git* — would conflict
   with the package's copy on every upgrade. dpkg's conffile handling is
   for `/etc`, not for a YAML the application edits. **Closed by backlog #1
   (2026-09-20) — see [Relocatable state](#relocatable-state) below.**
2. **First start builds nine images on the target**, needing the internet
   in four places and, on a Pi 5, minutes per Python image (matplotlib) —
   the three images that embed `common/` took about ten minutes together to
   rebuild with warm base layers during the v2.9.0 work. A package install
   that ends in a twenty-minute build with no progress bar is not "simple".
3. **Source bind-mounts** (`web-admin/app`, `smokeping-exporters`) point
   into `/opt`, which works but means the package is the code the
   containers run — fine for a package, but the "dev mount" comment on
   web-admin is then a lie, and an `apt upgrade` changes code inside a
   running container without a restart.
4. **config-manager writes generated output as root** into a directory the
   package owns; upgrades would tread on it. It belongs in `/var/lib`.
5. **Helper scripts hard-code `pro-influxdb-1`, `pro_default`,
   `grafana-influx_*`** and Compose v1 invocations; harmless while the
   project name stays `pro`, but a package should not depend on it.

## What has to change — the backlog

Ordered so each step is useful on its own and unblocks the next. Costs are
rough engineer-days for someone who knows the repo.

### Relocatable state

Done 2026-09-20. Three variables decide where the state the stack rewrites
lives; unset, everything stays beside the edition's compose file, untracked
by git, exactly where it was:

| Variable | What | Default (from a clone) | Packaged |
| --- | --- | --- | --- |
| `SMOKING_PI_ENV_FILE` | the secrets and settings `setup.sh` generates | `editions/<edition>/.env` | `/etc/smoking-pi/env` |
| `SMOKING_PI_CONFIG_DIR` | `targets.yaml`, `probes.yaml`, `sources.yaml` — the YAML config-manager edits (import/export; PostgreSQL is the source of truth) | `editions/<edition>/config-manager/config` | `/etc/smoking-pi/config` |
| `SMOKING_PI_OUTPUT_DIR` | the generated SmokePing `Targets`/`Probes` (Pro; Standard keeps them in a named volume) | `editions/pro/config-manager/output` | `/var/lib/smoking-pi/output` |

The two directories are read by the compose files themselves
(`${SMOKING_PI_CONFIG_DIR:-./config-manager/config}:/app/config`), so they
work with a bare `docker compose` as long as they are exported or in the
env file; relative values are relative to the edition directory, as every
other path in those files. The env file is different: Compose only finds
`./.env` on its own, so a relocated one has to be named on every call.
`setup.sh --env-file`, `generate-passwords.sh --env-file`,
`show-passwords.sh`, `manage-containers.sh` and the `smoking-pi` command
all read `SMOKING_PI_ENV_FILE` and pass `--env-file`; the `.deb` sets all
three in `/etc/default/smoking-pi`, which the systemd unit loads and
`postinst` creates the two directories for.

**Seeding.** A fresh config directory holds nothing (from a clone, a
`.gitkeep`). config-manager's bootstrap copies the three YAML files from
its own `templates/` on first start — the same mechanism that has recovered
a deleted file since Sprint 3 — and then generates the output. The image no
longer carries a `config/` copy, and the stale
`shared/modules/config-manager/{config,output}` copies (five probes,
untouched since Sprint 3, never read by anything) are gone; `templates/` is
the one seed set, and a test holds it to the current probe list. Verified
by running the rebuilt image against an empty directory: three files, the
HTTP/TCP probes among them, `Probes` and `Targets` generated.

**What this changes on the reference Pi:** nothing at runtime — the
defaults are the old paths, and the untracked files stay where they are.
`git status` is clean for the first time since the stack went live. CI
renders both compose files with the packaged layout and fails if a mount is
hardcoded again.

**Still true:** `smoking-pi install` refuses an existing env file, because
regenerating secrets against live volumes breaks authentication; `upgrade`
is backlog #4.

### Own repository or a distribution's?

Own. A Debian or Raspberry Pi OS package must build from source and cannot
depend on pulling container images at first start; a package whose payload
is compose files pointing at pinned upstream images is exactly what those
policies exclude. An apt repository on GitHub Pages costs one signing key
and one workflow step and gives `apt upgrade`. Third-party channels
(Homebrew tap, a Snap) are the same package with a different wrapper and
can follow once the apt path is proven.

### Target platforms

1. **Raspberry Pi OS (Debian 12/13, arm64)** — the reference; everything is
   built and verified here. Pi 4 and 5.
2. **Ubuntu 22.04/24.04, amd64 and arm64** — nothing in the repo is
   architecture-conditional; all upstream images are multi-arch; #3 makes it
   a first-class target by building for it.
3. **macOS via Homebrew** — with the fidelity caveat above.
4. **Podman**: not supported and not planned — config-manager needs the
   Docker socket and the compose files use v2 semantics (`profiles`,
   `depends_on.required`, `network_mode: host`).

### Lifecycle, end to end (target state)

| Step | Command | What happens |
| --- | --- | --- |
| Install | `apt install smoking-pi` | Code under `/opt/smoking-pi`, CLI, unit; nothing runs yet |
| Configure | `smoking-pi install` | Edition, backend, profiles (TUI or flags); secrets into `/etc/smoking-pi/env`; images pulled; first start; passwords shown; OpenClaw offered |
| Boot | `systemctl enable smoking-pi` | `up` after Docker; `down` at shutdown |
| Status | `smoking-pi status`, `smoking-pi doctor --live` | Compose state; the doctor's checks |
| Upgrade | `apt upgrade && smoking-pi upgrade` | New tree and CLI; new images pulled; `up -d` restarts what changed; doctor after. Stateful majors (PostgreSQL, InfluxDB) are excluded from routine upgrades exactly as they are excluded from Dependabot today; `smoking-pi backup` before a major |
| Failure | `smoking-pi logs <service>` | And the doctor's `deployed-code-current` says whether the container matches the package |
| Remove | `apt remove` / `apt purge` / `smoking-pi purge` | Code; +config; +volumes, in that order, the last one only on explicit confirmation |

## What this does not change

The architecture. Nothing above splits or merges a service, and the
host-network trio stays host-network. The question was whether the shape
fits a package; it does, once the package stops needing the checkout. The
Docker dependency also stays: it is the reason four upstream projects cost
nothing to maintain here, and removing it would mean alternative A.
